## 课前准备：环境复核（5 分钟，课前完成）

本讲的实验对象是 task-manager，下一讲开始写云书签。动手之前，先确认你的开发环境能被复现：换一台机器，照着项目里的文件就能装出一模一样的环境。

### 1. 为什么要虚拟环境和 requirements.txt

项目 A 要用 Flask 2.0，项目 B 要用 Flask 3.0。如果两个项目共用一个全局 Python 环境，只能装一个版本，必然有一个项目跑不起来。所以：

- **每个项目一个虚拟环境**（`venv/`），依赖装在项目自己的目录里，互不干扰；
- **用 `requirements.txt` 记下依赖的精确版本**，格式是「包名==版本号」。`pip freeze > requirements.txt` 生成它，`pip install -r requirements.txt` 在任何机器上还原。

### 2. 对照你的 task-manager 检查

```bash
cd ~/task-manager
ls -a                          # 应能看到 app.py、requirements.txt、.gitignore、.env、venv/
cat requirements.txt           # 每一行都写死了版本号
cat .gitignore                 # 应排除 venv/ 和 .env
git log --oneline              # 至少有一次提交
```

**检查点**：四条命令的结果与注释一致。哪一条对不上，回到《云原生 12 要素课堂教学项目》第一部分补做。

### 3. 一个 Web 项目的标准结构

下一讲新建的云书签项目，也是这个结构：

```
cloud-bookmark/
├── app.py
├── requirements.txt
├── .env          # 放密钥等配置，不提交
├── .gitignore
├── README.md
└── venv/         # 虚拟环境，不提交
```

三件工具各管一件事：Python 运行代码，VS Code 编写代码，Git 记录修改。Git 的四个概念：**仓库**（项目及其全部历史）、**提交**（一次修改的快照）、**分支**（一条独立的开发线）、**远程仓库**（放在服务器上的副本，如 GitHub）。

## 项目一　报文侦探

### 1. 项目目标

1. 看到一次完整的 HTTP 请求和响应，认出报文的四个部分；
2. 通过不同的请求，观察 2xx、3xx、4xx 三类状态码，说出各自表示问题在哪一边；
3. 验证服务器按 `Content-Type` 解析请求体。

### 2. 对应知识点

| 知识点 | 教材 | 课件 |
|---|---|---|
| IP、端口与连接 | 2.2.5、2.2.6 | P9、P10 |
| 请求报文的结构、常用请求头 | 2.2.3 | P14、P15 |
| HTTP 方法的语义 | 2.2.3 | P19、P20 |
| 响应报文的结构、常用响应头 | 2.2.4 | P16、P17 |
| 状态码 | 2.2.4 | P22—P25 |

### 3. 环境准备

实验对象是你已经跑通的 task-manager。它是一个 JSON 接口应用，`/tasks` 地址支持查看（GET）和新建（POST）两种操作。

在 WSL 的 Ubuntu 终端里启动它：

```bash
cd ~/task-manager
source venv/bin/activate
python app.py                 # 看到 Running on http://127.0.0.1:8000 即可，这个终端不要关
```

再打开**第二个** Ubuntu 终端，下面的命令都在这里执行。

**注意**：所有命令都在 WSL 里执行，不要在 PowerShell 或 CMD 里执行，否则中文和引号可能出错。

### 4. 实验步骤

#### 步骤 1　看一次完整的请求和响应（课上讲到 P13 时先做）

```bash
curl -v http://127.0.0.1:8000/tasks
```

**观察**：`*` 开头的行是 curl 与服务器建立连接的过程，`>` 开头的行是你发出的请求，`<` 开头的行是服务器返回的响应。

**对应知识点**：先连接、再通信（P10）；请求报文的四个部分（P14）、响应报文的四个部分（P16）。

**思考**：curl 连接的是哪个 IP、哪个端口？请求里的 `Host` 头是什么值？请求和响应各有一个空行，分别在哪里？GET 请求有请求体吗？

#### 步骤 2　成功：查看与新建

```bash
curl -i http://127.0.0.1:8000/tasks
curl -i -X POST http://127.0.0.1:8000/tasks -H "Content-Type: application/json" -d '{"title": "写实验报告"}'
```

`-i` 表示只显示响应（状态行、响应头、响应体），`-X POST` 指定方法，`-H` 添加请求头，`-d` 写请求体。

**观察**：两次的状态码分别是多少？响应的 `Content-Type` 是什么？

**对应知识点**：200 与 201 的区别（P23）；POST 的数据放在请求体里，格式由 `Content-Type` 说明（P15）。

**思考**：再执行一次第一条命令，结果有什么变化？这说明两个方法中哪个修改了服务器上的数据？

#### 步骤 3　请求有问题：服务端拒绝

```bash
curl -i -X POST http://127.0.0.1:8000/tasks -H "Content-Type: application/json" -d '{"title": ""}'
```

**观察**：状态码是多少？响应体说了什么？

**对应知识点**：4xx 表示请求有问题，需要改请求（P22）；400 表示参数错误（P23）。

#### 步骤 4　同样的数据，换一种格式

```bash
curl -i -X POST http://127.0.0.1:8000/tasks -d "title=写实验报告"
```

这条命令没有声明 `Content-Type: application/json`，curl 会按表单格式发送。

**观察**：和步骤 2 的第二条命令相比，数据内容一样，结果却不同。

**对应知识点**：服务器靠 `Content-Type` 决定怎样解析请求体（P15）。

#### 步骤 5　地址不存在与方法不对

```bash
curl -i http://127.0.0.1:8000/nothing
curl -i -X DELETE http://127.0.0.1:8000/tasks
```

**观察**：两个状态码分别是多少？第二条的响应头里有一个 `Allow`，它列出了什么？

**对应知识点**：404 与 405 的区别（P23）；「地址存在、方法不对」和「地址不存在」是两种不同的错误。

#### 步骤 6　浏览器里的重定向（需要外网，不通可跳过）

1. 打开浏览器，按 F12 打开开发者工具，切到 **Network**（网络）面板，勾选 **Preserve log**（保留日志）；
2. 在地址栏输入 `http://github.com`（注意是 `http`）；
3. 在请求列表里找到状态码为 3xx 的那一条，点开，查看响应头里的 `Location`。

**对应知识点**：3xx 表示需要客户端再走一步，`Location` 给出新地址（P17、P23）。

#### 步骤 7　回看服务器日志

回到第一个终端，看 task-manager 打印的日志。

**观察**：每个请求都有一行，包含方法、路径和状态码。和你刚才执行的命令一一对上。

**对应知识点**：这是第7讲排错时要看的「第一现场」，现在先认识它。

### 5. 观察记录表

| # | 请求（方法和路径） | 状态码 | 响应的 Content-Type | 一句话：发生了什么，责任在谁 |
|---|---|---|---|---|
| 1 | GET /tasks | | | |
| 2 | POST /tasks（JSON，有标题） | | | |
| 3 | POST /tasks（JSON，标题为空） | | | |
| 4 | POST /tasks（表单格式） | | | |
| 5 | GET /nothing | | | |
| 6 | DELETE /tasks | | | |
| 7 | GET http://github.com（浏览器） | | | |

### 6. 思考题

1. 第 2 行和第 4 行发送的数据相同，为什么一个成功、一个失败？
2. 第 6 行响应头里的 `Allow` 告诉了你什么？405 和 404 有什么区别？
3. 七行里有没有 5xx？如果出现 5xx，说明问题出在哪一边？

### 7. 完成标准

- 观察记录表 7 行填完（第 7 行网络不通时可以空着）；
- 每一行的「一句话」说清楚是成功（2xx）、重定向（3xx），还是请求的问题（4xx）；
- 三道思考题都有答案，每题一两句话。

## 项目二　云书签 S0：定接口表

### 1. 项目目标

在写代码之前，先把云书签对外提供哪些操作想清楚：每个操作用什么方法、什么 URL，成功和失败时各返回什么。第4讲就照这张表写路由。

这一步对应 CDIO 的**构思**与**设计**阶段：先定对外接口，再实现。

### 2. 对应知识点

| 知识点 | 教材 | 课件 |
|---|---|---|
| HTTP 方法的语义（安全、幂等） | 2.2.3 | P19 |
| 方法选择的原则（修改数据不用 GET；表单只支持 GET、POST） | 2.2.3、2.2.7 | P20 |
| 常见状态码 | 2.2.4 | P23 |
| HTTP 在 Web 应用中的实践（方法与 URL 的映射） | 2.2.7 | 本节「范例」 |

### 3. 需求背景

本章的云书签只做**书签管理**：查看列表、添加、编辑、删除。页面由后端生成，用户通过 HTML 表单提交数据，数据暂存在内存里。另外，云平台需要一个**健康检查**地址，用来判断应用是否在正常运行。

**范例：留言板的方法与 URL**（教材表 2-1）。方法按操作语义选择，URL 表示被操作的资源：

| 操作 | 方法 | URL | 说明 |
|---|---|---|---|
| 查看所有留言 | GET | `/messages` | 获取资源，不修改数据 |
| 提交新留言 | POST | `/messages` | 创建资源，数据在请求体中 |
| 编辑留言 | POST | `/messages/42/edit` | 修改资源 |
| 删除留言 | POST | `/messages/42/delete` | 表单只支持 GET、POST |

42 是留言编号：对某一条留言的操作，URL 里要带上它的编号。云书签的接口表就是把这个思路用到书签上。

### 4. 步骤（小组 3—4 人）

1. **列出操作。**把用户会做的每一件事列出来。注意：「打开添加表单」和「提交表单」是两次不同的请求。
   对应知识点：一次操作就是一次请求—响应（P6）。
2. **选方法。**逐个判断：这个操作会不会修改服务器上的数据？会的就不能用 GET。再判断：页面只有 HTML 表单，能发出哪些方法？
   对应知识点：P19、P20。
3. **定 URL。**URL 表示「对哪个资源操作」。对某一条书签的操作，URL 里要带上它的编号，例如 `/edit/<id>`。
   对应知识点：P27 路径；方法与 URL 的映射见上面的范例。
4. **写返回。**成功时返回什么？失败时又返回什么（比如编辑一条不存在的书签）？
   对应知识点：P23。

### 6. 完成标准

- 覆盖查看、添加、编辑、删除、健康检查五类操作；
- 会修改数据的操作，没有一个用 GET；
- 小组能说出删除为什么选了这个方法。

## 常见问题

遇到报错或结果与预期不符时，先在下表中查找。

| 现象 | 原因 | 处理 |
|---|---|---|
| `curl: (7) Failed to connect to 127.0.0.1 port 8000` | 连接没有建立（课件 P10）：task-manager 未启动，或启动它的终端已关闭 | 在第一个终端执行 `python app.py`，并保持该终端打开 |
| 响应中的中文显示为 `\u5199\u5b9e…` | JSON 对中文的转义写法，不是乱码 | 无需处理 |
| 第 3、4 行返回 400 | 预期结果，正是本实验要观察的现象 | 无需处理，照实填写记录表 |
| 第 2 行也返回 400，或命令中的单引号报错 | 命令在 PowerShell 或 CMD 中执行，中文编码与引号的处理不同 | 改在 WSL 的 Ubuntu 终端中执行 |
| 第 7 行看不到 3xx | 浏览器缓存了 HTTPS 跳转 | 在 Network 面板勾选 Disable cache（停用缓存）后重试；网络不通时跳过此步 |
